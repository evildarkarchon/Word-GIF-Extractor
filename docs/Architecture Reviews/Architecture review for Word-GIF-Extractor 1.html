Decide conversion fallback by Image write purpose, once

Strong in-process

Before
After
Problem
What a fallen-back conversion means is decided twice, in two visitors, and the purpose is spelled into four warning variant names. The preparation tests can't reach either decision.
Solution
Preparation reads the source's Image write purpose and returns the final disposition plus one purpose-tagged warning. Both visitors only stage what it returns.
Wins
  • locality: fallback rule in one match
  • 4 warning variants become 2
  • interface is the test surface
  • leverage: Document extraction wording shrinks
  • base_name stops leaking into facts
Open question first: a cover that is found but then filtered out or fails conversion ends Completed, so --cover-fallback does not fall back (pinned at cover_extraction/tests.rs:227). The README says an EPUB with "no usable cover" falls back. Deepening forces this to be one explicit rule. Decide which reading is intended.
ADR-0022 left "unifying the two visitors' per-image paths" out of its scope without forbidding it. ADR-0017 (tally) and ADR-0020 (purpose on the source) are untouched; this builds on 0020.

Fold a whole Document extraction outcome into the run outcome

Strong in-process small
  • src/extraction_run.rs (:197-217)
  • src/extraction_run_observation.rs (fold :247, record_failed_document :266, finish :276)
Before: two-call protocol
match extract(doc) → (facts, Option<error>)
acc.fold(&facts)
if error { acc.record_failed_document() }
nothing ties call 2 to call 1; forget it and failures vanish from the outcome
acc.finish(cover_only)
After
let outcome = extract(doc)
acc.fold(&outcome)
tally added · failed count follows from the variant
acc.finish(cover_only)
Problem
The run splits each Document extraction outcome apart and has to remember a second accumulator call for failures.
Solution
The accumulator takes the Document extraction outcome itself, so the failed-document count is set by construction, the way ADR-0017 made the totals.
Wins
  • interface shrinks: one fold
  • failure count by construction
  • accumulator tests cover failure classification

Problem
ImageWritePipeline holds only its policy plus two forwarders, and the Output placement is passed untouched through about six signatures before Image file emission uses it.
Solution
Document extraction binds the pipeline to the Selected document's Output placement once; the DOCX and EPUB adapters receive that single value.
Wins
  • locality: placement known in one place
  • delete one pass-through module
  • adapter signatures shrink
Consistent with ADR-0022, which already binds Image file emission to one Output placement. ADR-0018 and ADR-0022 left the policy forwarders out of scope. Keep Image write policy as the owner of the Applicable outcome facts (ADR-0018).

Give the GIF destination one route to the Extraction run outcome

Speculative in-process

  • src/emitted_image_tally.rs (TallyRole :15)

Before: two routes, never compared
After (first step only)
Problem
The destination reaches emission through the role and reaches the outcome through a second chain. Nothing checks that they agree, and tests/ has no --gif-output test.
Solution
Start with the end-to-end CLI test. Collapse the two routes only if that test or a real bug shows the chain is costing something.
Wins
  • GIF routing pinned at the binary
  • decision deferred until it earns an ADR
Collapsing the routes contradicts ADR-0017/0022 (the role carries its destination) and ADR-0018 (the Applicable outcome facts chain). Not worth reopening yet; the CLI test contradicts nothing.
Seen and set aside
• A test constructor for Selected document. Extraction tests run real Document selection to get one, but the glossary says only Document selection grants it.
• Bundling run_with's parameters into one struct. ADR-0018 §4 rejected this.
• Moving the outcome accumulator into the Extraction run. That needs a ProducedOutput constructor, which ADR-0017 deleted.
• Rerouting the warning path so adapters return Document extraction facts. The translation is already concentrated in one place in Document extraction, so the deletion test says this would only move it.
Top recommendation

1 · Decide conversion fallback by Image write purpose, once

The Image write pipeline is the most-changed module in the recent history, and this is the one place in it where a single rule is still decided twice. Deepening it also forces an answer on whether --cover-fallback should cover a cover that was found but unusable. After that, candidate 2 is a clean follow-up that ADR-0019 already set up.
