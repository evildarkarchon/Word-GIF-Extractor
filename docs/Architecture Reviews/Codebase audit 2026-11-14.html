Codebase audit: word-image-extractor

14 November 2026 · commit e3ce9fb5f on main · crate version 0.3.0 · independent of the earlier reviews in this folder

The internals are in good shape; the behaviour at the edges is not. The build is green, the lint gate is clean, and the core pipeline is carefully modelled. But driving the release binary with realistic documents turned up four high-severity defects that the 327 passing tests do not see: ordinary EPUB title pages are written out as .svg "images", deduplication silently drops distinct books, the run summary disappears whenever stderr is not a terminal, and putting -f before the input path redirects the run to the whole current directory.

The common cause is that every test fixture is a minimal synthetic archive. The code is tested thoroughly against the shapes its authors imagined and not at all against the shapes Calibre and Word actually produce.

Implementation status, 17 November 2026. The six small, contained fixes (H4, M1, H1, M7, L2 and M8 step 1) are fixed in PR #112, which also takes M8 step 2, the zip major upgrade. H2 is fixed in PR #113 (ADR-0025). H3 is fixed (ADR-0026), not yet merged. Those findings carry a status badge and an Implementation note. Everything else, including every transcript, count and line reference, is the audit as written at e3ce9fb5f.

Baseline on this commit: cargo build --release succeeds, cargo test passes all 327 tests, cargo clippy --all-targets -- -D warnings is clean, and cargo fmt --check reports no differences.

Of the 25 findings, thirteen were reproduced by running the release binary, six rest on measurements from cargo and rustc or on direct observation of the repository, and six are read from the code without being executed. Each finding carries a badge saying which.

Method and limits

  • Read in full: all production source under src/ (every file except tests.rs modules and test_support.rs), Cargo.toml, README.md, GLOSSARY.md, AGENTS.md.
  • Read in part: the 23 ADRs (opening section of each; ADR-0014 whole), the integration tests and both test-support modules (sampled, plus searches for specific coverage).
  • Executed: the build, test, clippy and fmt gates; cargo tree, cargo update --dry-run and cargo search for dependency facts; and the release binary against eleven small fixture files built for this audit (described in the appendix).
  • Not done: no run on a real terminal (the harness has none, so the on-terminal half of H3 is inferred from the progress library's documented behaviour); no Linux or macOS run; no security advisory scan, because neither cargo-audit nor cargo-deny is installed; no line-by-line review of the test code; peak memory in M6 was not measured.
  • Earlier reviews: not used as input. ADRs 0017 to 0024 are treated as binding and any recommendation that touches one says so. ADRs 0001 to 0016 are treated as open and assessed in their own section.

High severity

H1

EPUB pages that contain inline SVG are extracted as .svg images

HighFixed · PR #112Reproduced src/image_write_pipeline/discovery.rs:372-383

is_svg accepts any resource whose first 1,024 bytes contain <svg anywhere. Magic bytes outrank the declared MIME type, and EPUB normal-image extraction sniffs every manifest resource, so an XHTML page that wraps an image in inline SVG is identified as an SVG image and written out. That is exactly the title page Calibre generates for every book it converts, so most Calibre-produced EPUBs yield one bogus .svg file containing HTML.

$ word-image-extractor fixtures/calibre -o out/calibre
$ ls out/calibre
Some Author - Calibre Book_1.jpg
Some Author - Calibre Book_2.png
Some Author - Calibre Book_3.svg        ← titlepage.xhtml
$ head -c 96 "out/calibre/Some Author - Calibre Book_3.svg"
<?xml version='1.0' encoding='utf-8'?>
<html xmlns="http://www.w3.org/1999/xhtml" xml:lang="en">

The bogus file also takes an ordinal, is counted in the summary, and with --convert produces a "format not supported for conversion" warning. A fixture comment at src/test_support.rs:977 states that an XHTML resource "is declared as application/xhtml+xml, so extraction never treats it as an image"; that holds only because the fixture's body is empty.

Recommendation

Require <svg to be the document's root element: skip a BOM, whitespace, an XML declaration, comments and a doctype, then demand <svg. That keeps byte-first discovery intact for genuine SVG files with weak labels. The neighbouring signatures deserve the same look: BMP is accepted on two bytes (BM, line 313), which any text resource beginning with those letters satisfies.

Implementation: is_svg now skips a BOM, whitespace, processing instructions (the XML declaration among them), comments and doctypes, internal subset included, within the same 1,024-byte window, and then requires <svg followed by a delimiter. A prolog construct left unterminated inside the window is not evidence. A namespace-prefixed root such as <svg:svg> is not recognized from bytes; it still reaches SVG through its extension or declared MIME. BMP now also needs a known DIB header size (12, 16, 40, 52, 56, 64, 108 or 124) at offset 14, not just the two letters. A Calibre-style title page is tested both on the recognizer and through discovery, and the fixture comment in src/test_support.rs now says it is the bytes, not the declared MIME type, that decide.

H2

EPUB deduplication silently drops books that are not duplicates

HighFixed · PR #113Reproduced src/document_selection/phases.rs:203-278 src/document_selection/document_identity.rs:121-131

Every run deduplicates EPUBs by case-folded creator and title, with no flag to turn it off and no mention in the README. Three realistic inputs lose documents:

  • Periodicals and serials whose issues share one creator and title: only the first issue is processed.
  • Creator-only metadata. An absent title becomes an empty string in the key, so every title-less book by one author collapses into one.
  • Undeclared EPUBs with the same file name in different directories are treated as one book on the name alone.
$ ls fixtures/serial                  # three issues, each: creator "The Weekly", title "The Weekly"
weekly-2026-01.epub  weekly-2026-02.epub  weekly-2026-03.epub
$ word-image-extractor fixtures/serial -o out/serial ; echo exit=$?
exit=0
$ ls out/serial
The Weekly - The Weekly.png           ← one image; two issues were never opened

$ word-image-extractor fixtures/creator_only -o out/creator   # first.epub, second.epub: creator "Jane Doe", no title
$ ls out/creator
Jane Doe.png

The only trace is "Removed 2 duplicate EPUB(s)" on the progress display, which names no file and, per H3, is invisible when stderr is redirected. The run exits 0.

Recommendation

  1. Report each dropped EPUB as a Document selection diagnostic naming both the dropped path and the one it duplicated, as SkippedNonEpubInput already does for its case.
  2. Tighten the key. The package's dc:identifier is the field designed for this: issues of a periodical differ in it and true copies share it. Fall back to creator plus title only when both are declared, and never treat a path identity as a duplicate of a file in another directory.
  3. Add an opt-out (--keep-duplicates) and document the behaviour in the README.

ADR note: ADR-0019 (binding) governs the repeat-sighting collapse and the join order, not identity-based deduplication, so none of this contradicts it. The Document identity entry in GLOSSARY.md would need its duplicate-recognition sentence revised.

Implementation: All three recommendations are in, and ADR-0025 records the decision. EpubDeclarations now carries the identifier the package's unique-identifier attribute names. The duplicate key is that identifier together with the creator and title, all trimmed and case-folded. Without an identifier, an EPUB has a key only when it declares both a creator and a title. An EPUB that declares neither, or cannot be read, has no key, so file names never collide. One difference from the recommendation: the identifier does not decide alone. The creator and title stay in the key beside it, so a placeholder identifier or an ISBN reused across volumes cannot merge different books. The cost is that a copy whose identifier was stripped is kept rather than recognized. Each skip is a new SkippedDuplicateEpub { path, duplicate_of } diagnostic, rendered as Warning: Skipped <path>: it declares the same book as <kept> (use --keep-duplicates to extract both). It is reported for EPUBs found by a directory search too, and does not change the exit status. --keep-duplicates keeps every EPUB. The phase still runs under the flag, because it is where an unfiltered EPUB gets the declarations its output name comes from. The README gains a Duplicate EPUBs section, and GLOSSARY.md revises Document selection, Document identity and Document selection diagnostic. tests/epub_deduplication_cli.rs reproduces the serial, creator-only and same-name cases against real archives, plus a true copy with and without the flag.

H3

The run summary vanishes whenever stderr is not a terminal

HighFixedReproduced src/extraction_run_presentation.rs:534-539 :243-252

For every run that selects at least one document, the terminal summary is delivered by finishing the progress bar with the summary as its message. The progress library hides its stderr target when stderr is not a terminal, so under a pipe, a redirect, a scheduled task or CI the summary is never written anywhere. A successful run is completely silent:

$ word-image-extractor fixtures/docx/thumb.docx -o out/E > stdout.txt 2> stderr.txt ; echo exit=$?
exit=0
stdout: 0 bytes    stderr: 0 bytes        # two files were written

The same applies to "No images found", "No cover images found", "Found N matching EPUB(s)" and "Removed N duplicate EPUB(s)". There is also a stream inconsistency: "No documents found to process." goes to stdout (no display is live), while every other summary goes to stderr through the display. A script cannot capture the result line from one place.

The capture harness cannot see this, because RecordingTerm always behaves like a terminal.

Recommendation

Treat the summary as output, not as progress decoration: clear the live display, then print the summary line to stdout in every case. Give TerminalOutput::captured a non-terminal mode (a hidden draw target) and pin the summary with it.

ADR note: this revises the routing rule in ADR-0013 ("the terminal summary finishes the live display or, when none is live, is printed to standard output"). ADR-0013 is expired and open for re-evaluation; the transcript design it also records is unaffected.

Implementation: The recommendation is in, and ADR-0026 records the decision. It replaces ADR-0013's summary routing rule and keeps its transcript. The progress display now carries only lines that may disappear when the run moves on. The terminal summary clears whatever display is live with finish_and_clear, then prints to standard output in every case, so "No documents found to process." and every other summary share one stream. One extension of the recommendation: the phase conclusions this finding lists, "Found N document(s)", "Found N matching EPUB(s)" and "Removed N duplicate EPUB(s)", follow the same rule. Each is printed after its phase's display clears, and still only when that phase raised a display, so non-recursive discovery adds no line. TerminalOutput::captured_without_terminal is the non-terminal mode. It draws to ProgressDrawTarget::hidden(), the target the progress library substitutes off a terminal, and keeps the one ordered transcript. The library still exports four items. In-crate tests pin that each summary and conclusion follows a clear and is never drawn, and that a hidden-display run reports conclusions, a warning and its summary in order. A new test in tests/binary_smoke.rs runs the compiled binary with both streams piped and requires standard output to be exactly the summary line. It failed before the change with both streams empty, as in the transcript above. The README gains an Output section saying which stream carries what.

H4

-f placed before the input path swallows the path and retargets the run

HighFixed · PR #112Reproduced src/extraction_run_intake.rs:83-84

--formats is declared with num_args = 0.., so it keeps consuming arguments after the comma-separated list. In the conventional flags-first order, the document path becomes a format token. It is then "ignored" as unrecognized, no input remains, and intake falls back to the current directory:

$ cd fixtures/docx
$ word-image-extractor -f png,jpg thumb.docx -o ../../out/A
No input path specified, using current directory: …/fixtures/docx
Warning: Unrecognized format 'thumb.docx' ignored
$ ls ../../out/A
colors_1.png  colors_2.png  colors_3.png  thumb_1.jpg  thumb_2.png   ← every document in the directory

The user asked for one file and the tool processed the whole working directory, exit 0. Without -o it would also have written beside every one of those documents.

Recommendation

Take exactly one value per occurrence: num_args = 1 with the existing value_delimiter = ',' (and ArgAction::Append if repeating the flag should accumulate). Add a parse test for -f png,jpg file.docx. Combined with M3, an unrecognized token would then be an error instead of a detour.

Implementation: --formats takes one comma-separated value per occurrence (num_args = 1 with ArgAction::Append), so repeating the flag accumulates and a bare -f is a parse error. Parse tests cover -f png,jpg file.docx in both spellings, repetition, and the missing value. M3 is untouched: an unrecognized token is still a warning, not an error.

Medium severity

M1

Lossy WebP conversion fails on every grayscale and 16-bit image

MediumFixed · PR #112Reproduced src/conversion.rs:339-344

webp::Encoder::from_image implements only 8-bit RGB and RGBA and returns Err("Unimplemented") for everything else. Grayscale scans and line art are common in books, so --convert webp leaves a large share of real images unconverted.

$ word-image-extractor fixtures/docx/colors.docx -C webp -o out/webp
Warning: Conversion failed for word/media/image1.png: WebP encoder creation failed: Unimplemented   # 8-bit gray
Warning: Conversion failed for word/media/image2.png: WebP encoder creation failed: Unimplemented   # 16-bit RGB
$ ls out/webp
colors_1.png  colors_2.png  colors_3.webp

The same file converts completely with -C jpg and with -C webp --lossless, which go through the image crate's encoders. No conversion test uses a non-RGB8 source.

Recommendation

Normalize before encoding: to_rgba8() when the colour type has alpha, otherwise to_rgb8(), then Encoder::from_rgba or from_rgb. Add grayscale, gray-alpha and 16-bit cases to src/conversion/tests.rs for all three targets.

Implementation: encode_webp_lossy normalizes with to_rgba8() when the colour type has alpha and to_rgb8() otherwise, then encodes through Encoder::from_rgba or from_rgb. src/conversion/tests.rs converts L8, La8, L16, Rgb16 and Rgba16 sources to JPEG, PNG, lossy WebP and lossless WebP. It also checks that lossy WebP keeps an alpha channel exactly when the source has one. The matrix test fails against the old encoder.

M2

Cover detection misses common EPUBs, and a book with no candidate says nothing

MediumReproduced src/epub_declarations.rs:25 src/document_extraction/epub/cover_extraction.rs:25,95
  • EPUB 3 with the EPUB 2 cover meta. The epub crate's get_cover_id reads only properties="cover-image" for version 3 packages and only <meta name="cover"> for version 2. A version 3 package that carries just the meta element, which is widespread, has no declared cover.
  • The filename candidate is JPEG-only. cover.png and cover.webp are never considered.
  • No candidate, no message. When neither candidate exists, the document writes nothing and warns nothing. The README says such an EPUB's "warnings say why".
# EPUB 3 package: <meta name="cover" content="front"/>  +  <item id="front" href="images/front.png" media-type="image/png"/>
$ word-image-extractor fixtures/epub3 --cover-only -o out/epub3 ; echo exit=$?
exit=0                                 # no file, no warning, no output directory

Recommendation

Try both declarations whatever the package version; widen the filename candidate to any supported raster extension; emit one Document extraction warning when a cover run finds no candidate at all, so a batch shows which books had none.

ADR note: ADR-0021 and ADR-0023 (both binding) describe two candidates in a fixed order. This keeps their rules (first written cover wins, hand-over on a candidate that writes nothing, fallback exactly when none was written) and lengthens the candidate list, which should be recorded as an amendment rather than slipped in.

M3

A typo in --formats widens the run to every format

MediumFixedReproduced src/extraction_run_intake.rs:287-289

If no token is recognized, the allowed set silently becomes all ten formats. A filter flag that fails open does the opposite of what was asked, with exit 0.

$ word-image-extractor fixtures/docx/thumb.docx -f pgn -o out/B
Warning: Unrecognized format 'pgn' ignored
$ ls out/B
thumb_1.jpg  thumb_2.png

Recommendation

Reject unknown tokens at parse time with a clap value_parser (exit 2, listing the valid names). If compatibility matters more, at least fail when every token was rejected. The comment at line 266 calls the current behaviour "existing compatibility behavior"; this is a deliberate change to it.

Implementation: The first recommendation is in, and ADR-0027 records the decision. Args::formats is now Option<Vec<ImageFormat>>. A private TypedValueParser in intake hands each token to ImageFormat::from_user_format, so jpeg, tif and any case still parse, and every other token is a clap invalid-value error: invalid value 'pgn' for '--formats <FORMATS>' followed by the ten canonical names, exit 2, nothing searched or written. One bad token rejects the whole flag, even beside valid ones, and an empty token (png,,jpg, -f "") is reported as a missing value. --help now lists the possible values. PreRunNotice::IgnoredFormat and its warning are gone, and with them the all-formats fallback. Intake unit tests cover aliases, a lone typo, a typo among valid tokens and the empty cases. tests/binary_smoke.rs runs the compiled binary with -f pgn and checks the exit status, the message and the missing output directory. tests/pre_run_notices_cli.rs now pins only the defaulted-input notice, and the README's --formats row lists the names.

M4

A named input that is missing or unsupported still exits 0, the latter without a word

MediumReproduced src/document_selection/discovery.rs:86-95,118 src/extraction_run_presentation.rs:61-64 
$ word-image-extractor nope.docx ; echo exit=$?
Warning: Input path does not exist: nope.docx
No documents found to process.
exit=0
$ word-image-extractor fixtures/docx/notes.txt ; echo exit=$?
No documents found to process.           # no hint that the extension is the reason
exit=0

A script that passes a wrong path gets success. A user who passes report.doc or book.mobi gets a message that reads as though the file were empty.

Recommendation

Distinguish what the user named from what a directory search turned up; CandidateOrigin already carries that. A named path that does not exist, or names an unsupported kind, should be reported as an error and make the exit status 1. An empty directory sweep stays 0.

ADR note: this revises ADR-0014 (expired). Its stated reason for exit 0 was that "presentation labels it a warning, and an exit status that disagreed with the label would be a second classification drifting from the first". That argues for changing both together, not for keeping either.

Implementation: Both are in, and ADR-0028 records the decision. Requested-input classification now rejects a named path that does not exist, or that is neither a directory nor a file whose extension names a supported document kind; a named device counts too. The rejection is decided on the requested root before discovery opens, so CandidateOrigin was not needed. Each is reported once, as MissingInput or the new UnsupportedInput, and rendered as Error: Input path does not exist: nope.docx or Error: Input is not a .docx or .epub file or a directory: notes.txt. The selection lifecycle counts each rejection in the method that reports it. select_documents returns that count beside the Selected documents. Every outcome variant carries it, so NoDocuments is now a struct variant. run_cli exits 1 when reported_an_error is true, which means a failed document or a rejected input. Other inputs still run and the summary is unchanged. An unsupported file found by a directory search stays silent, so an empty sweep still exits 0. A named input that exists but cannot be inspected, such as a broken link, deliberately stays a warning. Unit tests cover the count and its boundary in selection, the accumulator seed, the run outcome, the wording and run_cli's status. tests/document_selection_diagnostics_cli.rs runs a missing, an unsupported and a readable input together and checks exit 1, both error lines and the extracted image. The README's exit-status section and the glossary say the same.

M5

The DOCX adapter sniffs every ZIP entry, so preview thumbnails become image 1

MediumFixed · PR #117Reproduced src/document_extraction/docx.rs:32

The adapter visits all entries, not the media folder. Word's optional docProps/thumbnail.* (the file-manager preview) is therefore extracted as a document image. ZIP order puts it first, so it renumbers the real images and turns a single-image document's name.png into name_2.png.

# thumb.docx holds docProps/thumbnail.jpeg and word/media/image1.png
$ word-image-extractor fixtures/docx/thumb.docx -o out/thumb ; ls out/thumb
thumb_1.jpg      ← the preview thumbnail
thumb_2.png      ← the document's only image

Recommendation

Limit the traversal to media parts (word/media/; matching */media/* would also serve the other Office formats, see Opportunities), or at minimum exclude docProps/.

ADR note: ADR-0020 (binding) holds that "no name is grounds for a silent skip". It was written about unreadable sources and about names never reaching an output path, and this would be an eligibility rule rather than a guard, but it is close enough to that sentence that it should be decided explicitly.

Implementation: Both the fix and the Opportunities item are in, and ADR-0029 records the decision, including why it is an eligibility rule rather than the silent skip ADR-0020 forbids. The extension decides an Office package and the package decides the one media folder that holds document images: word/media/, ppt/media/, xl/media/, visio/media/, or Pictures/ for OpenDocument. The Office adapter, renamed from docx.rs to office.rs, skips every entry outside that folder before reading it, so docProps/thumbnail.* and LibreOffice's Thumbnails/thumbnail.png are neither written, numbered nor warned about. An entry whose name cannot be decoded is still offered, because the adapter cannot show it lies outside the folder. Selection now accepts every ZIP-packaged Word, PowerPoint, Excel, Visio and OpenDocument extension, including the macro-enabled, template and show variants and .xlsb, and carries the package on the Selected document. SelectedDocument::Docx became SelectedDocument::Office. The unsupported-input error names one extension per suite. Unit tests cover the extension table and the folder rule in office_package, the thumbnail case and each suite's folder in the adapter, and every suite's package in selection. A mutation that disables the folder check fails all four new adapter tests. tests/office_documents_cli.rs runs the audit's thumb.docx and checks it writes thumb.png alone, then runs a .pptx, .xlsx, .vsdx and .odt with thumbnails through a directory search. The README gains a Supported Documents table and the glossary gains Office document and Office package.

M6

Accepted entries are buffered whole with no size limit

MediumFixed · PR #118Output reproducedMemory: from code src/image_write_pipeline/discovery.rs:241

Identification is bounded to 1,027 bytes, but an accepted entry is then read to the end into a Vec before anything is written, and conversion decodes a second copy. Nothing checks the entry's declared or actual size. A 522 KB document built for this audit inflated to a 512 MiB output file:

$ ls -l fixtures/big/big.docx     →  521,999 bytes
$ word-image-extractor fixtures/big/big.docx -o out/big ; ls -l out/big
536,870,920  big.png

For a local tool run on one's own library this is a robustness concern more than a security one, but a batch over downloaded books is exactly where a malformed archive turns up, and with panic = "abort" an allocation failure ends the whole run.

Recommendation

Set a per-entry ceiling (configurable, generous by default) and turn an oversize entry into a Document extraction warning. When no conversion is requested, stream the remainder of the reader into the reserved file instead of buffering; the naming lookahead only needs to hold back the first image.

Implementation: Both recommendations are in, and ADR-0030 records the decision. It amends ADR-0022, which stays binding. Every archive image source is held to an Image size limit, 256 MiB unless --max-image-size sets another. The flag takes a byte count or a K, M or G binary suffix, and rejects zero, decimal units such as MB and overflow at parse time. The limit is checked against the bytes read, never the size the ZIP header declares. An entry past it writes nothing and warns Skipping <entry>: larger than the 256 MiB image size limit (raise it with --max-image-size). An oversize EPUB cover writes no cover, so the next candidate is tried. One difference from the recommendation: streaming covers every image whose bytes are kept, not only runs without conversion. That includes a routed GIF, a source already in the conversion target, and a format that cannot be converted, such as EMF, WMF or SVG. The conversion policy now answers those cases from the format before anything is decoded. Images that are converted, and each document's first image, which the naming lookahead holds back, are still buffered, up to the limit, with growth capped so the buffer never doubles past it. A streamed image that arrives while the first is held back is written before it. If the arrival's source runs short, its partial file is removed and the first image keeps the singular name. Measured on Windows with this audit's 512 MiB fixture, peak working set fell from 1,030 MiB to 262 MiB when the entry is a document's only image, now skipped with a warning, and to 5.3 MiB when it follows another image and is written. Unit tests cover the limit's spelling, both ways of consuming a payload, the arrival-first order, and a streamed file filling while its source is still being read. Mutations that buffer the stream or write the held-back image first each fail them. tests/image_size_limit_cli.rs runs an oversize second image and two 1.5 MB images through a real ZIP. The README gains an Image Size Limit section, and the glossary gains Image size limit.

M7

Warnings do not say which document they belong to

MediumFixed · PR #112Reproduced src/extraction_run_presentation.rs:745-749,766-768

The DocumentWarning observation carries the document path, and presentation discards it. Entry names repeat across documents (word/media/image1.png is in nearly every DOCX), so a batch produces lines that cannot be traced:

$ word-image-extractor colors.docx colors2.docx -C webp -o out/I
Warning: Conversion failed for word/media/image1.png: WebP encoder creation failed: Unimplemented
Warning: Conversion failed for word/media/image2.png: WebP encoder creation failed: Unimplemented
Warning: Conversion failed for word/media/image1.png: WebP encoder creation failed: Unimplemented
Warning: Conversion failed for word/media/image2.png: WebP encoder creation failed: Unimplemented

Recommendation

Prefix the path presentation already receives: Warning: colors2.docx: Conversion failed for …. The warning body stays owned by Document extraction; only the prefix changes.

Implementation: Lines now read Warning: <path>: <body>. One difference from the recommendation: the prefix is the document path as the run observed it, not its file name. That matches the existing Error processing <path> line and keeps two documents that share a name in different folders apart. The two tests that pinned the old rule (no document path in a warning) now assert that the path sits between the prefix and the unchanged body.

M8

Dependencies: seven majors behind on zip, two copies of it, and unused codecs compiled in

MediumSteps 1–2 fixed · PR #112Measured Cargo.toml:7,11 Cargo.lock
  • zip is locked at 2.4.2; crates.io currently lists 9.5.1.
  • The tree holds two zip versions: 2.4.2 (direct) and 3.0.0 (through epub). Each EPUB is opened and its central directory parsed once by each.
  • zip is used with default features, which compile AES, bzip2, xz, zstd, zopfli, LZMA, deflate64 and time. DOCX and EPUB use stored and deflate only.
  • Cargo.lock was last changed on 10 July; cargo update --dry-run lists several dozen pending compatible updates. No advisory scanner is installed, so known-vulnerability status is unchecked.
  • The epub crate brings regex, xml-rs, thiserror and the second zip, to supply four facts: title, creator, cover id and the manifest. Its limits are also the cause of M2.

Recommendation

  1. Now: zip = { version = "…", default-features = false, features = ["deflate"] }, refresh the lockfile, and add cargo audit or cargo deny to the gate.
  2. Then: plan the zip major upgrade; the surface used here is small (ZipArchive::new, by_index, index_for_name, name_for_index).
  3. Consider replacing epub with a direct read of META-INF/container.xml and the OPF through a small XML parser. One archive handle, one zip version, deterministic manifest order without a re-sort, and cover rules the project controls.

ADR note: item 3 reopens ADR-0001 (expired), which weighed keeping EpubDoc against forking the crate or buffering eagerly. Reading the package document directly was not among the options it considered.

Implementation: zip is now 9.6.0 with default-features = false, features = ["deflate"]: the same major version and features that epub 2.1.6 asks for. The tree therefore holds one zip, and each EPUB's central directory is parsed by one implementation. Refreshing the lockfile moved epub from 2.1.5 to 2.1.6, which took its own copy to 9.x. Unique crates in the normal dependency tree fell from 136 to 98. The only API break was name_for_index, which now returns Option<ZipResult<Cow<str>>>; both callers treat a name that fails to decode like a missing one. cargo deny check advisories joined the gate in AGENTS.md. A lockfile refresh alone would have left zip 2.6.1 with four RustSec advisories (RUSTSEC-2026-0367, -0368, -0369 and -0429), all in ZipArchive::extract and ZipStreamReader::extract, which this crate never calls. After the upgrade, cargo audit and cargo deny report none. Step 3, replacing epub (ADR-0001), is still open.

M9

There is no CI, so the gate and the Unix code paths rely on memory

MediumFixed · PR #119Observed no .github/ directory

AGENTS.md defines "done" as tests plus clippy passing, and nothing enforces it on a pull request. The test support carries #[cfg(unix)] branches (src/test_support.rs:739-793, tests/support/mod.rs:371-404) that a Windows-only workflow never compiles, and L3 describes behaviour that differs by platform. Cargo.toml declares no rust-version although the source needs a recent compiler (edition 2024, let-chains).

Recommendation

One GitHub Actions workflow on windows-latest and ubuntu-latest: fmt check, clippy with -D warnings, test, and the advisory scan from M8. Declare rust-version.

Implementation: .github/workflows/ci.yml runs on every pull request, on pushes to main, weekly, and on demand. Clippy with -D warnings and cargo test --no-fail-fast run on windows-latest and ubuntu-latest, both with --locked and with fail-fast off, so a failure on one platform does not cancel the other. cargo fmt --check runs as its own job, so a formatting slip does not skip the tests. cargo deny check advisories runs once on Linux, because the action needs a Linux container and advisories describe the lockfile, not the host. The weekly run catches an advisory published against an unchanged lockfile. Cargo.toml now declares rust-version = "1.88". Edition 2024 needs 1.85 and let-chains need 1.88, and zip 9.6 and image 0.25.10, the highest declarations in the dependency tree, also need 1.88. A fourth job reads that field and runs cargo check --all-targets on that compiler, so the floor is tested rather than stated. AGENTS.md adds cargo fmt --check to the gate the workflow enforces, and the README states the minimum Rust version. Before the push, the workflow passed actionlint, and the whole gate plus a 1.88 build passed on Windows. The first Linux run compiled the #[cfg(unix)] test support cleanly. It failed one test, names_a_skipped_copy_and_keeps_it_when_asked, because ext4 listed b-copy.epub ahead of a-original.epub and the original was skipped as the duplicate. That is L3, which is fixed in the same pull request. Plain cargo test stops at the first failing test binary, so the workflow passes --no-fail-fast. With it, the Linux run reported that one failure and nothing else.

Low severity and polish

L1

Re-running a command duplicates every output file

LowReproducedsrc/image_write_pipeline/emission.rs:187-209

Emission never overwrites, which is the right default, but there is no way to ask for anything else. Three runs of the same command leave thumb_1.jpg, thumb_1_1.jpg, thumb_1_2.jpg and the same for every other image. Offer --skip-existing (or skip when an existing file has identical bytes) and --overwrite.

L2

The summary never mentions failed documents

LowFixed · PR #112From codesrc/extraction_run_presentation.rs:771-836

The outcome carries failed_documents and only the exit status reads it. A run can end "Extracted 5 image(s) from 2 document(s)" after failing on thirty. ADR-0014 itself notes the wording was left for later; append ", N document(s) failed" to each template.

Implementation: , N document(s) failed is appended once, after whichever template the outcome selects, including No images found and No cover images found. Tests cover a produced outcome, both no-output outcomes, and the combined conversion and GIF-routing template.

L3

Output names depend on the operating system's directory order

LowFixed · PR #119Reproduced in CIsrc/document_search_surface.rs:171-188

read_dir and WalkDir are used unsorted. Emission claims names first come, first served, so which of two documents sharing an Output placement gets the unsuffixed names follows encounter order, and so does which EPUB survives deduplication. NTFS happens to list alphabetically; ext4 does not. Sort both (WalkDir::sort_by_file_name, and collect-then-sort for the flat listing). Names would move only where the OS order was not already sorted.

Implementation: M9's first Linux run reproduced this: tests/epub_deduplication_cli.rs skipped a-original.epub as a copy of b-copy.epub, because ext4 listed the copy first. ADR-0031 records the decision and amends ADR-0008. The filesystem surface now yields each directory in file-name order, through WalkDir::sort_by for the traversal and collect-then-sort for the flat listing. Entry read failures come first in both, as walkdir orders them. One difference from the recommendation: names compare case-insensitively, by their uppercase form, with an exact-byte tie-break, rather than through sort_by_file_name's raw bytes. NTFS orders names that way, so output on Windows stays where it was, and Linux and macOS now match it. A byte sort would have put B.epub ahead of a.epub and moved names for Windows users. A comparator test pins the order on every platform. A conformance test creates files against the expected order and checks both listings. Replacing the comparator with a byte comparison fails both. The README's Duplicate EPUBs section says which copy is first, and the glossary's Document search surface entry gains the order.

L4

Discovery stats every traversed entry before looking at its extension

LowFrom code, unmeasuredsrc/document_selection/discovery.rs:144,200

Each entry gets a followed fs::metadata call even when its name already rules it out, on top of the file type the directory walk supplied for free. On a large tree that is one extra syscall per file, and it produces "Could not inspect" warnings for broken links to things that were never documents. Check the extension first and inspect only candidates; that also removes most of the stale-entry branches in the recursive arm.

L5

Filename sanitisation has no length limit and ignores Windows device names

LowFixedReproducedsrc/document_selection/document_identity.rs:210-220

An EPUB's base name is "creator - title" with illegal characters replaced. A long subtitle can exceed the 255-character component limit, which fails the whole document with a create error. A title of NUL, CON, AUX or COM1 yields a name Windows may treat as a device. Truncate to a safe length on a character boundary and prefix reserved stems.

Implementation: Reproduced on Windows 11 with LongPathsEnabled set: a 256-unit name fails with os error 123, while a 550-character path writes fine, because Rust's standard library already gives long paths the \\?\ form. The cap is on one name, so long-path awareness cannot lift it and no manifest was added. ADR-0032 records the decision. Image file emission now fits every candidate name in src/image_write_pipeline/emission/file_name_fit.rs, rather than Document identity, because the ordinal, collision suffix and extension are known only there (ADR-0022). This also covers an Office stem that goes over once numbered. Unlike the recommendation, a name is shortened only when it is over 255 units, so every name that worked before is unchanged. Length is counted in UTF-16 units on Windows and UTF-8 bytes elsewhere. An overlong base is cut on a character boundary to leave a 16-unit reserve for the suffix and extension, so all of a document's images keep one stem. A name whose part before the first dot is a device name gains a leading _ on every platform. Windows 11 no longer treats NUL.png as a device, but Windows 10 does. Unit tests pin the rule, an emission test writes overlong names and their collisions to disk, and tests/output_name_fitting_cli.rs runs the audit's two cases end to end. With fitting disabled, those tests fail with the original create error.

L11

LowFrom codesrc/conversion.rs:285-304

What is solid

Archive names never reach the filesystem

Output paths are built only from the Output placement and a canonical extension. A hostile entry name (../../x) has nothing to influence, so the classic zip-slip class is closed by design.

Writes cannot clobber or leave debris

Files are reserved with create_new, collisions advance a suffix, and a failed write removes its partial file, with the handle dropped first for Windows.

Counts are correct by construction

The Emitted image tally and the closed role enum make inconsistent totals unrepresentable. No assertion re-checks them because none is needed.

Presentation is testable end to end

The one-transcript capture lets a test assert ordering across stdout, stderr and the progress display, and even that a line was written while the display was suspended.

A clean, fast gate

327 tests run in about a second once compiled; clippy is clean at -D warnings with not one #[allow] in production code.

A shared vocabulary that is used

GLOSSARY.md terms match the module and type names one for one, which made this audit considerably faster to perform.

Opportunities beyond defects

  • Other ZIP-based documents. The DOCX adapter is already a generic "images in a ZIP" reader. Accepting .docm, .dotx, .pptx, .xlsx and .odt is mostly an extension table once M5 defines which entries count.
  • A dry run. --dry-run listing what would be selected, skipped as duplicate, and written would make H2-style surprises visible before any file exists.
  • Per-document subfolders. With -o, two documents that share a base name interleave their collision suffixes; an option to write each document into its own folder removes the ambiguity.
  • Parallel conversion. Documents are processed one at a time and conversion is CPU-bound. Parallelism would have to preserve the first-come naming order ADR-0019 fixes, so decode and encode in parallel and emit in sequence.
