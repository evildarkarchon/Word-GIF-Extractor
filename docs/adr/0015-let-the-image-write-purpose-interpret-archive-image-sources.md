# Let the Image write purpose interpret Archive image sources

`ArchiveImageSource` had two constructors, `named` and `required_cover`, and they differed in one field: `path_evidence_name` was `Some` for a normal source and `None` for a cover. That one `Option` carried two decisions belonging to the Image write purpose — whether a normal source is eligible, because `is_normal_source_safe` treats a missing name as unsafe, and whether the name may serve as Image format evidence — and the document adapter made both by picking a constructor. Nothing tied that choice to the entry point the adapter then called, so a cover-built source handed to the normal-image visitor was rejected without a warning and the image silently vanished. The Archive image source therefore becomes purpose-neutral: one constructor taking a name, with an optional declared MIME, and nothing that encodes eligibility or evidence. The entry point the adapter calls selects the Image write purpose, and the purpose decides what the source's facts mean.

Eligibility and path evidence become one purpose decision rather than two. For normal images they are a single judgement about a single string — is this name trustworthy — and the old shape derived them separately from the same field, which is how the two could drift apart. The purpose now answers with either a rejection or permission to inspect carrying the name it accepts as path evidence, which a required cover never supplies. Archive image discovery threads that answer into identification and the extension-fallback warning instead of reading the source a second time.

Two protocol changes follow from the same rule that the caller should not be able to say something the pipeline cannot mean. The normal-image visitor takes one acquisition result per source — a reader, or the error explaining why the resource was unavailable — instead of offering `visit` and `unreadable` as separate methods, so source eligibility is applied once to both cases and the unsafe-name silent skip is no longer re-implemented beside discovery. The required cover stops being a traversal at all. `write_required_cover` used to take a closure and then check at runtime that the closure supplied exactly one source, with an error for none and another for more than one; it now takes the source and its acquisition result directly. The EPUB resource archive's scoped `acquire` is already generic over its return value, so the cover write runs inside the payload scope and returns its outcome through it. `RequiredCoverWriteVisitor`, its disposition and both runtime protocol errors are gone, and "exactly one source" is a property of the signature. `ImageWriteRequest` and `RequiredCoverWriteRequest` were field-for-field identical and are merged under the first name with one purpose-neutral constructor, since the purpose is now chosen by the entry point rather than by the request.

Inverting control was considered and rejected, and it is the alternative a future review is most likely to propose again. Under it, DOCX and EPUB would each implement a crate-private trait yielding archive image sources and the pipeline would drive the loop, which looks deeper: the DOCX adapter would shrink to a trait implementation and the acquire-then-visit step would be written once. The cost is where the loop would move. EPUB cover extraction falls back to normal images while excluding the Archive resource identities its attempts already touched, and ADR-0005 puts that exclusion behind `CoverAttempts::fallback` in the EPUB adapter, which owns the traversal it filters. A pipeline-driven loop would have to take the exclusion across a new seam, and the EPUB resource archive's scoped payload acquisition — the shape ADR-0001's incremental reads depend on — would have to fit a trait method rather than a closure. The closure-taking visitor already gives tests an in-memory seam, so inversion would change who owns the loop without changing what can be tested; it saves a few lines per adapter, and that is not enough to move the exclusion rule.

Three smaller alternatives were also rejected. Keeping both constructors and making a mismatch a compile error, through visitors generic over a source-kind marker, would add type machinery to guard a choice the adapter should not be making at all. A pipeline-owned acquisition enum with readable and unavailable variants would be a second name for `Result`, which already means "this, or why not" and composes with `map` and `?`. And renaming the merged request after output placement was declined because that term already names a fact Document selection decides, and a per-document placement value may yet be introduced on Document extraction's side of the seam; borrowing the name now would leave that change two near-synonyms.

The scope is deliberately narrow. The change preserves behaviour exactly: the same files, names, warnings, warning order and counts, including the silent skip of an unsafe-named source that also fails to open and the order in which discovery warnings precede conversion warnings. `ImageWritePurpose` remains a trait with static dispatch; only the single-variant `FilteredFormatAction` is removed, because an action with no choice forces discovery to destructure a value it cannot branch on. The `Option` returned by `prepare_image_for_write`, which ADR-0007 left to the purpose trait, is still out of scope, as are the normal-image output flag that Document extraction reads to classify covers-only output and any per-document binding of the pipeline with its placement. `CoverAttempts`, `CannedAttempts` and `EmittedImageRole` are untouched, so ADR-0005 and ADR-0007 stand as written.

This decision is recorded ahead of the change it governs, in the manner of ADR-0006 and ADR-0007. Nothing here becomes public: ADR-0003 still governs the library interface, and every item involved stays crate-private.
