# Search directories in file-name order

The 2026-11-14 audit (L3) found that Document discovery took each directory's contents in the order the operating system reports. ADR-0008 wrote that into the Document search surface: a directory listing comes "in the order the world reports" and a traversal yields entries "in encounter order", and the filesystem surface passed `read_dir` and `WalkDir` through unsorted. Encounter order is not cosmetic. Image file emission claims names first come, first served (ADR-0019), so it decides which of two documents sharing an Output placement gets the unsuffixed names. EPUB deduplication keeps the first of two copies, so it also decides which copy is extracted and which is reported as skipped. NTFS lists a directory alphabetically, ignoring case. ext4 lists it in hash order. The first CI run on Linux (M9) showed the consequence: `tests/epub_deduplication_cli.rs` named `a-original.epub` and `b-copy.epub`, Linux encountered the copy first, and the original was the one skipped.

The filesystem surface now sorts. Both the flat listing and the recursive traversal yield each directory's contents in file-name order, and the two use one comparator. The recursive traversal sorts through `WalkDir::sort_by`, which orders one directory's entries before descending into any of them. The flat listing collects `read_dir` and sorts it. A failure to read one entry has no name to sort by. `walkdir` puts such failures ahead of the directory's entries, and the flat listing does the same, so the two listings agree on failures as well as names.

## The comparator

Names compare case-insensitively, by their uppercase form, and names that are equal once folded compare by their exact bytes. The audit suggested `sort_by_file_name`, which compares raw bytes. That would put `B.epub` ahead of `a.epub` and `_x.epub` between the cases, which is not how NTFS lists them. Windows is where this tool has been used, and its order there was already deterministic, so a byte sort would have moved output names for exactly the users who had no problem. Folding to uppercase is how NTFS compares names, so on Windows the order is unchanged for every name the two foldings agree on, and Linux and macOS now agree with it. The byte tie-break makes the order total. Without it, `Book.epub` and `book.epub`, which can sit side by side on a case-sensitive filesystem, would compare equal, and their order would fall back to whatever the sort's input order was.

The fold is Unicode's full uppercase mapping, not NTFS's own upcase table, so the two can differ on a few characters whose uppercase form is longer than the original, such as `ß`, which uppercases to `SS`. Those names still get one fixed order on every platform, which is what this decision is for. A name that is not valid Unicode, which Linux allows, folds lossily, and the byte tie-break still tells two such names apart.

## Where the sort lives

The sort lives in the filesystem surface, not in Document discovery, although ADR-0008 generally prefers logic that every surface implementation shares. Discovery could sort the flat listing it receives, but not the traversal: the order of a recursive walk is decided one directory at a time inside `walkdir`, together with `skip_current_dir`, and discovery sees only the resulting stream. Sorting there would mean reimplementing the walk. The declared surface used in Document selection's tests yields entries in the order a test scripts, which is what those tests want. The surface's own conformance tests pin the order, and a comparator test pins it on Windows too, where NTFS would pass an unsorted listing anyway.

## Consequences

ADR-0008 is amended, not replaced. Its seams, its vocabulary and its reasons for both stand. Only "in the order the world reports" becomes file-name order for the filesystem surface. Encounter order across directories is still a depth-first walk, and named inputs are still taken in the order the command line gives. Output names move only where a directory was not already listed in this order: on Linux and macOS, and on Windows for names where Unicode and NTFS fold differently. Sorting a directory holds its listing in memory before the first entry is yielded. A directory holds names, not payloads, so this costs little.

`GLOSSARY.md`'s Document search surface entry says the filesystem surface lists in file-name order. The README's Duplicate EPUBs section says which copy counts as first. Nothing here becomes public: ADR-0003 still governs the library interface, and the comparator is private to the surface.
