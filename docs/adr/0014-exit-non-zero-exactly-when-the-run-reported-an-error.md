# Exit non-zero exactly when the run reported an error

The binary exits with status 1 when at least one selected document failed to extract, and with status 0 when none did. A run that found no documents, or found documents with no images, exits 0: finding nothing is an answer rather than a failure, which is how `find` treats an empty result and not how `grep` treats a missed match, and scripts that sweep directories which may be empty should not start failing. Every non-fatal problem presentation prints as a `Warning:` line — a missing requested input, a discovery failure, unreadable EPUB metadata, a document extraction warning — also leaves the status at 0. A document failure is printed as an `Error processing` line, so the rule a user can check against the terminal is that the run exits non-zero exactly when it printed an error. Partial failure counts, as it does for `cp` given several files: the run still processes every other document and still reaches its summary, and then exits 1. Status 1 is shared with intake failures, which already exited 1 through `main` returning an error, and command lines `clap` cannot parse keep `clap`'s own status 2. A distinct status for document failures was considered and not taken, because the scripts this serves test whether the tool failed rather than why.

Treating a missing requested input as a failure, as `ls` does for a missing operand, was rejected for now because presentation labels it a warning, and an exit status that disagreed with the label would be a second classification drifting from the first. Making "no documents" or "no output" a failure was rejected for the reason above.

Before this, the Extraction run outcome could not express a failure at all. The accumulator folded a failed document's facts exactly like a completed one's, and the failure existed only as an observation, so "every document failed" and "the documents held no images" were the same `NoOutput`. The outcome now carries `failed_documents`, a count that is either absent or positive, on `NoOutput` and on produced output, built by construction as ADR-0006 builds the rest of the outcome. `NoDocuments` carries no count, because a run that selected nothing had nothing to fail. The run records a failure at the point where it reports the document's error, so the outcome counts a failure exactly when the terminal shows one.

The decision is the run's and the number is the CLI's. `run_cli` maps the outcome to a `std::process::ExitCode` and returns it as the success value of its `Result`, and an intake failure still travels as the error; `main` returns that `Result` unchanged. Having presentation count the errors it renders was rejected, because presentation owns no decisions and the outcome is where the run's classification lives. Calling `std::process::exit` inside the library was rejected because it skips destructors and cannot be observed by an in-process test. Returning a library-defined status type was rejected because it would be a fifth exported item against ADR-0003; `ExitCode` is the standard library's, so the interface still exports exactly four items, and `run_cli`'s changed return type is the only widening.

The terminal summary does not mention failures yet. The fact is now in the outcome, so adding wording is a presentation change whenever it is wanted.
