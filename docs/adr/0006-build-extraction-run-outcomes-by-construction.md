# Build Extraction run outcomes by construction

The Extraction run outcome is accumulated by a value owned by the Extraction run observation module, seeded from Applicable outcome facts, folded with the Document extraction facts of each document, and finished into an `ExtractionRunOutcome` that cannot fail. The Extraction run no longer keeps a private aggregation that mirrors the outcome types field for field, and `RunAggregation`, `ConversionAggregation`, `GifRoutingAggregation` and `into_outcome` are gone with it. The `expect("run aggregation must produce consistent semantic totals")` those three types existed to justify is gone as well, and this ADR is mostly about why deleting it required a change somewhere other than the outcome.

`ExtractionRunOutcome::try_produced` rejects a produced outcome whose documents or whose classified output exceed its emitted-image total. The Extraction run could only satisfy that check because the Image write pipeline returns early for routed GIFs, leaving the routed and converted sets disjoint, so an invariant was validated in the observation module, asserted away in the Extraction run, and made true by a control-flow decision in the Image write pipeline. Moving the fold into the observation module does not by itself discharge that: an accumulator finishing with the same check would have relocated the assumption rather than removed it. The invariant is therefore enforced where pipeline counts become Document extraction facts, in `DocumentExtractionFacts::from_image_write_result`, as a `debug_assert!` that the converted, conversion-skipped and GIF-routed counts do not together exceed the emitted count. That seam is the one place that sees both the pipeline's accounting and the run-facing facts. Once every document's facts satisfy the rule, the sums satisfy it too, and each document contributing to the document count contributes at least one emitted image, so both of `try_produced`'s branches are discharged by the fold and `finish` needs no fallible path. A violation is a pipeline regression rather than a runtime condition, which is why it is a debug assertion and not a document-local failure; the existing boundary-case test that pins three emitted images as one converted, one skipped and one routed is what would catch it.

`try_produced` nevertheless stays, and collapsing it into the accumulator would be a mistake. The two constructors answer different questions: the accumulator is valid by construction and is the only path production takes, while `try_produced` validates arbitrary input and is how Extraction run presentation's tests build one outcome to render without assembling a run's worth of state. Its own unit test exercises exactly that validation. A future reader who finds two ways to build a produced outcome should not read the second as leftover.

The accumulator is seeded from Applicable outcome facts rather than from the Image write policy that owns those facts, and that is load-bearing rather than incidental. ADR-0004 left the observation module with exactly one outward edge, to `DocumentExtractionWarning` in Document extraction, and folding Document extraction facts adds nothing in a new direction. Naming `ImageWritePolicy` here would have added a second outward edge, to the Image write pipeline, for the convenience of reading two fields directly — which is the coupling ADR-0004 spent a module removing. For the same reason the per-document output-purpose classification is a Document extraction type rather than a reuse of `ExtractionOutputKind`: that type lives in the observation module, which already depends on Document extraction, so importing it back would close the cycle ADR-0004 exists to prevent.

Two smaller decisions follow the same rule that a type should mean one thing. The run's cover intent reaches `finish` as an argument rather than riding inside Applicable outcome facts, because that value answers which optional fact groups apply and cover intent is classification input; the zero-output case needs it precisely when there are no per-document purposes left to fold. And Document extraction facts expose one emitted-image totals value and one output-purpose classification instead of four count accessors and a normal-image boolean, so the counter shape is named once rather than re-spelled at every hop. `get_gifs_routed` had no caller but the aggregation it fed, and does not survive the change.

Applicable outcome facts themselves were considered for removal and kept. The three-hop chain from the Extraction run through Document extraction to the Image write policy looks like a round trip of facts that Extraction run intake held when it assembled the policy, but the Image write policy is their single owner and the Extraction run request deliberately retains nothing derived from the policies it carries. Caching the two facts at construction would trade one indirection for a copy that construction would have to keep correct, which is a worse bargain than the one the existing code struck.

This decision is recorded ahead of the change it governs. At the time of writing the Extraction run still assembles its outcome through the private aggregation trio described above, and the ADR exists so that whoever implements the change, and anyone reviewing it later, shares the reasoning rather than rediscovering it. Nothing here becomes public: ADR-0003 still governs the library interface, and every item involved stays crate-private.
