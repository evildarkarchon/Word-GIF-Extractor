# Record the capture as one ordered transcript

Extraction run presentation keeps one live progress display rather than one slot per phase. Phases never overlap, so the four `Option<ProgressBar>` slots only ever held one bar between them, and each diagnostic arm had to name the slot its phase owned; that choice is where a comment claiming every diagnostic suspended went stale, because the missing-input arm wrote directly. The single slot is tagged with the phase that drew it, so a phase's observations only advance or finish their own display, but presentation still learns nothing about phase order. Every write to standard error now suspends whatever display is live, and the terminal summary finishes the live display or, when none is live, is printed to standard output. The second rule replaces a no-documents special case and a silent drop: a summary for any other outcome used to vanish if no extraction display existed, which the run's ordering made unreachable but did not make impossible.

A captured destination records all three sinks — progress display, standard output, standard error — into one ordered transcript behind one lock, instead of two progress counters beside two separate text buffers. Suspension is a statement about order: the display clears, the line is written, the display draws again. Counters could not express that. The in-crate suspension tests snapshotted both counters around one observation and reported lower bounds, because a steady tick anywhere in the measured window added to both, and the integration tests could only assert that both counters were positive somewhere in the run. With one transcript the property is exact, because the progress library holds the display's lock for the whole of a suspend, so no tick can draw between a clear and the write it protects.

`Capture` therefore replaces `clear_lines()` and `writes()` with one question, `suspended_around(line)`: every write of that line, to either stream, has a clear as its nearest earlier progress entry and a draw as its nearest later one, and a line never written answers `false`. `stdout()`, `stderr()` and `progress_text()` remain, now read out of the transcript. Publishing the transcript itself was rejected: it needs a public entry type, a fifth exported item against ADR-0003, and it would make the recording granularity of the progress library part of the interface. Encoding the transcript as marked-up text was rejected for the same coupling without the type. Keeping the counters alongside was rejected because nothing would still need them, and a lower bound offered beside an exact answer invites the weaker assertion. In-crate tests read the private transcript directly when a whole sequence is the clearest assertion.

The two removed methods are a breaking change to what the library publishes, though not to its four items, which ADR-0003 fixes and this leaves unchanged. Should a caller ever need counts again, they are derivable from the transcript and can return as readers over it rather than as separate state.
