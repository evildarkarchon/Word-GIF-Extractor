# Reject a missing or unsupported named input as an error

The 2026-11-14 audit (M4) showed two command lines that did nothing and still exited 0. `word-image-extractor nope.docx` printed `Warning: Input path does not exist` and then `No documents found to process.` `word-image-extractor notes.txt` printed only the summary. Discovery passed over a named file with an unsupported extension in silence, exactly as it passes over one found inside a directory. So a script that passed a wrong path got success, and a user who passed `report.doc` or `book.mobi` was told, in effect, that the file held no documents.

A requested input is now rejected when it does not exist, or when it is neither a directory nor a file whose extension names a supported document kind. That includes an object that is neither a file nor a directory, such as a device. Requested-input classification decides this before the discovery phase opens, where the missing-input diagnostic was already decided. Each rejection is reported once, in input order: `MissingInput { path }` as before, or the new `UnsupportedInput { path }`. Presentation renders both as `Error:` lines on standard error, `Error: Input path does not exist: …` and `Error: Input is not a .docx or .epub file or a directory: …`. The extension check is the one discovery already applied, now `DocumentKind::of_path`, so `REPORT.DOCX` is still accepted.

Only what the user named is judged. An unsupported file found by a directory search is not a document and stays silent, which is why a named directory that holds no document still exits 0. `CandidateOrigin` was not needed for this: a rejected input never becomes a candidate, because the decision is made on the requested root itself. Naming a directory and also an unsupported file inside it rejects that file once.

Rejection is an error, and it changes the exit status. ADR-0014 kept a missing input at 0 because presentation labelled it a warning, and "an exit status that disagreed with the label would be a second classification drifting from the first". That argued for changing both together, so both change: the label is now `Error:`, and the run exits 1. ADR-0014's rule still holds in its own words, that the run exits non-zero exactly when it printed an error. Like a failed document, a rejection is partial failure, as `cp` treats an unreadable operand. Every other input is still selected and extracted, the summary is still printed, and then the run exits 1. The summary wording is unchanged: the error lines above it already say why fewer documents were found.

The count reaches the exit status by construction, as ADR-0006 and ADR-0014 build the rest of the outcome. The Document selection lifecycle counts each rejection in the method that reports it, so the count includes an input exactly when the stream reported it. `select_documents` now returns a `DocumentSelection` with the Selected documents and that count. The run did not read its own observation stream back to recover it. Every Extraction run outcome variant carries `rejected_inputs`, `NoDocuments` included, since the typo case selects nothing. `NoDocuments` becomes a struct variant to hold it. The outcome accumulator takes the count as a seed, because selection has finished before the first document is folded. `ExtractionRunOutcome::reported_an_error` is true when a document failed or an input was rejected, and `run_cli` maps that to `ExitCode::FAILURE`. The decision stays in the outcome and the number stays in the CLI. The library interface is unchanged.

Three diagnostics deliberately stay warnings and leave the status at 0. A named input that exists but cannot be inspected, such as a link whose target is gone, is reported through the same `DocumentDiscoveryFailed` fact as an entry a directory search could not inspect, and splitting that fact was more than M4 asked for. A named DOCX skipped because only EPUBs are eligible (ADR-0011) and a skipped duplicate EPUB (ADR-0025) are decisions about eligibility, not inputs the run could not use.

This changes behaviour on purpose. A command line naming a missing path or an unsupported file now exits 1 where it exited 0, and its message now starts with `Error:` rather than `Warning:`.
