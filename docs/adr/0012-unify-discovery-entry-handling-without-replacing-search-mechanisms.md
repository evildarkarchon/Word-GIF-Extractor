# Unify Document discovery entry handling without replacing search mechanisms

Document discovery will consume one directory-search operation on the Document search surface, selecting immediate children or recursive search, and use one loop for entry inspection, supported-document acceptance, progress, and diagnostics. The real adapter will retain `std::fs::read_dir` for immediate children and `WalkDir` for recursive search. This decision was accepted ahead of implementation; the first migration is now implemented as described below.

This supersedes ADR-0008's decision to expose directory listing and recursive traversal as two operations, while preserving its separation of requested-input classification from the adapter. The open equivalence question in that ADR has a concrete counterexample in the locked `walkdir` 2.5.0 implementation: if a requested directory becomes a file after discovery classifies it, `read_dir` reports a failure, whereas `WalkDir` with `min_depth(1)` and `max_depth(1)` excludes the reclassified root and yields nothing. Shallow `WalkDir` also performs entry classification before discovery's inspection and opens direct child directories before discarding work beyond its depth limit. Replacing direct listing with depth-limited traversal would therefore change observations, not merely remove duplicated code.

The shared interface will carry entries and failures in encounter order, with depth and failure-path information sufficient to preserve attribution. Entries will describe whether the search may descend through them, rather than require immediate-child listing to classify directories. Immediate-child search has no descent; recursive search retains the enumeration-time fact needed to prune a branch when later inspection finds that its directory disappeared or changed kind. Document discovery continues to own followed inspection, broken-link classification, candidate origin, and diagnostic decisions. The adapter owns acquisition mechanics, not document eligibility.

Compatibility requires preserving encounter order, selected documents, link handling, diagnostic attribution and ordering, progress, and continuation after failures. In particular, changing discovery order can change which EPUB survives first-occurrence deduplication. Encounter order means retaining each mechanism's reported order, not introducing sorting or promising that independent filesystem searches return the same order. Only underlying error-detail wording may differ; any other behavioral difference requires a separate decision.

The gain is depth at the existing seam: Document discovery learns one directory-search interface, while inspection and reporting decisions gain locality in one implementation. The real adapter and in-memory adapter keep the seam testable. Selection tests will retain their behavioral assertions through that interface, including unreadable-entry continuation, linked roots, stale-branch pruning, and pathless failure attribution. Real-adapter tests will cover immediate-child scope, reported order, link paths, and a root replaced after inspection. Tests may adapt how they invoke the interface without weakening their assertions. ADR-0003's narrow library interface remains unchanged.

## Implementation progress

Ticket 01 migrates immediate-child discovery through `DocumentSearchSurface::search` in both adapters. `SearchScope`, `DirectorySearch`, `SearchEntry`, and `SearchFailure` carry ordered acquisition, depth, optional failure paths, and possible descent. Immediate-child acquisition uses direct listing without entry metadata classification; opening failures enter the stream at depth zero with the requested root, and unreadable entries at depth one without a path. Discovery attributes pathless immediate-child failures to the requested directory and continues.

Recursive discovery remains on `traverse` with its existing consumption loop and pruning behavior. It shares the renamed vocabulary, and the recursive search scope delegates to that existing acquisition. Ticket 02 will migrate the recursive caller and consolidate the consumption loops. The in-memory adapter retains its existing declared tree encounter order and failure placement. No search-policy or public-interface change is part of this transition.
